# Issue #592: Data Crow XML/CSV export fixtures

## Status (2026-11-18)

As of 2026-11-18, **none of the 24 required Data Crow export captures is
present in this repository**. No Data Crow plugin, importer, test project, or
fixture directory exists; the only Data Crow-related artifact is this document.

No Data Crow instance is available to the project environment, so no team
member can operate the Item Export Wizard and produce a genuine export. Data
Crow is also GPLv3, which is a blocked license under
[`docs/legal/dependency-license-policy.json`](../legal/dependency-license-policy.json);
its sources, installers, and distribution files cannot be vendored or committed
here. Only a user running Data Crow can supply the exports described below.

This document is therefore the written statement required by the issue: **the
required exports for all six target modules are currently unobtainable by the
project**. It is a project availability gap, not a finding that any module
cannot be exported, and not permission to guess. A future donation closes the
corresponding captures through a tracked change that updates this document with
the accepted files and their provenance.

No implementation work may start from this document alone. Exact XML
element/attribute names come from observed files only; nothing below asserts a
Data Crow format fact.

## Capture procedure

All captures must be produced by a genuine, running Data Crow. Hand-written or
edited-in values are acceptable only as PII redaction of values within a real
export; an export that was authored from scratch, synthesized from documentation
or memory, or generated by a script that imitates the format is not a fixture
and must not be committed.

1. **Prepare a dedicated source catalog.** Ask the donor to create a new, small
   catalog containing only invented entries (titles, artists, authors, genres,
   paths, and notes that are not personal), or to use a throwaway copy of an
   existing catalog. Prefer invented content so redaction is minimal.
   Include content that exercises: multiple values in one field (for example
   several genres or authors on one item), non-ASCII text, empty optional
   fields, and at least one item with an image attached. If the UI offers
   loan/lend data, include one invented borrower; otherwise capture whatever
   the application exports and record the absence.
2. **Record the environment** before exporting: full Data Crow version (as
   shown by the application's own version display), platform, and UI language.
   Do not upgrade or downgrade Data Crow during the capture set.
3. **Movies: XML without copied images.** In the running application, select the
   Movies module and run **Tools > Item Export Wizard**. Choose XML, leave the
   copied-images option off, and export to an empty dedicated folder. Record
   every wizard screen and setting, including field selection, target folder,
   and any option whose wording differs from this document.
4. **Movies: XML with copied images.** Repeat the wizard with the copied-images
   option on, to a different empty folder. Do not reuse or overwrite the
   previous output.
5. **Movies: CSV without copied images**, then **Movies: CSV with copied
   images**, each as a separate wizard run and a separate folder. Record the
   CSV-specific settings (delimiter, text qualifier, encoding, header row) as
   offered.
6. **Repeat steps 3–5 for Music, Books, Images, Software/Games, and TV
   series.**
7. **Do not re-save the outputs.** Copy the produced files out of the target
   folders; never open CSV in a spreadsheet application and re-save it, never
   reformat XML with an editor or formatter, and never change line endings,
   encoding, or a byte-order mark. Those properties are themselves format
   evidence.
8. **Sanitize values only**, following the section below, then compute SHA-256
   checksums and commit. A file with an incomplete provenance record is not
   accepted.

If the wizard is unavailable, crashes, or produces an empty export for a
module, record the observed behavior, version, and settings; do not substitute
a different tool's output.

## PII stripping guidance

Exports are created from a catalog, and catalogs routinely hold personal data.
Review the **entire** file, not just the fields selected in the wizard, because
an export can include more than the selection suggests. Prefer a catalog built
from invented content; otherwise redact values in place.

- **Titles and names.** Replace item titles, artist/author/publisher/person
  names, and similar text with invented values. Preserve length and character
  variety where practical so encoding and width behavior remain testable.
- **Custom fields.** Free-text custom fields often hold names, addresses,
  e-mails, invoice numbers, or client names. Redact values. Field labels are
  format evidence and must not be renamed; if a label itself is personal, the
  source catalog was wrong for donation and a new synthetic catalog is required.
- **File paths.** Absolute paths expose usernames, share names, drive names, and
  client folder names. Replace path segments with generic ones while preserving
  separator style, depth, and extensions; do not collapse a path into an empty
  value, which would hide the field's shape.
- **Notes and descriptions.** Redact free text, including comments, review
  text, and HTML if present. Check for e-mail addresses, phone numbers, and
  URLs that identify a person.
- **Loan/lend borrower data.** Borrower names, contact details, and loan history
  are personal. Replace borrower values with invented names and dates; keep the
  field populated if it was populated in the original so the encoding remains
  observable, or record that the field was empty and why.
- **Images.** Copied images can carry EXIF GPS coordinates, camera serial
  numbers, timestamps, embedded thumbnails, XMP, and personal file names.
  Never commit a personal photo. Either use images that are synthetic from the
  start, or strip metadata and replace content with non-identifying images
  while keeping the file names and directory layout produced by the wizard.
  Record exactly what was replaced and re-compute checksums afterwards.
- **XML comments and hidden values.** Remove comments that contain personal
  notes. Do not delete whole elements or columns to hide data; that destroys
  structural evidence. If a value cannot be redacted without changing
  structure, the capture is rejected.
- **Do not "clean" empty or odd values.** Empty fields, placeholder values, and
  unusual characters are evidence. Leave them as exported.
- **Final check.** Search each file for `@`, absolute drive or volume paths,
  known usernames, and URL patterns, and have a second person review the diff
  between the processed file and the original before commit.

## Facts to establish from the fixtures

The following facts are **unconfirmed**. They must be read from donated files
and recorded in the importer's implementation note before any parser is
written. They must never be asserted from memory, third-party documentation,
forums, screenshots, or Data Crow source, and Data Crow source must not be
consulted or copied (GPLv3).

| Fact | Current status | Evidence required |
|---|---|---|
| Exact XML element and attribute names | **Unconfirmed (0/24 fixtures).** No name is known or assumed. | At least one accepted XML capture per module, with names recorded case-sensitively, including namespaces, nesting, attributes versus elements, and empty-element form. |
| Module identity marker | **Unconfirmed.** Whether an export names its module (root element, type attribute, field vocabulary, or nothing at all) is unknown. | Accepted captures for all six modules compared side by side; record whether the module can be identified from content alone or only from provenance and wizard settings. |

| Multi-value encoding | **Unconfirmed.** For XML: repeated elements, nested containers, or delimited text. For CSV: repeated columns, repeated rows, or a delimiter inside a quoted cell. Quoting, escaping, and line endings are also unknown. | Captures containing fields with more than one value, in both formats, with byte-level inspection. |

Until each fact is established from accepted fixtures, the corresponding
parsing and detection behavior cannot be designed. Guessing element names or
multi-value syntax would produce a parser that silently misreads catalogs.

## Handling untrusted exports

- Treat every donated file as untrusted input. Do not open exports in Data Crow,
  do not execute embedded content, and do not follow paths or URLs found inside
  a file.
- Do not open CSV captures in spreadsheet applications; formula-like text can
  execute and re-saving destroys quoting and encoding evidence.
- Validate only structurally before commit: a standard XML parser for
  well-formedness (without resolving external entities) and a plain CSV reader
  for column counts. Do not "repair" or normalize a file; a malformed export is
  a finding to record.
- Do not download Data Crow exports from third-party sites or accept files of
  unknown provenance.

## Where accepted fixtures must live

Accepted captures belong in the future Data Crow plugin's test project, in a
directory that follows the repository convention for format fixtures:

```
tests/SkyCD.Plugin.DataCrow.Tests/Fixtures/DataCrow/<CaptureID>/export.xml
tests/SkyCD.Plugin.DataCrow.Tests/Fixtures/DataCrow/<CaptureID>/export.csv
tests/SkyCD.Plugin.DataCrow.Tests/Fixtures/DataCrow/<CaptureID>/images/...
tests/SkyCD.Plugin.DataCrow.Tests/Fixtures/DataCrow/<CaptureID>/provenance.md
tests/SkyCD.Plugin.DataCrow.Tests/Fixtures/DataCrow/README.md
```

Each capture gets its own directory so images and text cannot be confused
between runs. The README indexes every capture with its checksums, module,
format, and copied-images state, in the style of
[`tests/SkyCD.Plugin.CdCollect.Tests/Fixtures/Sqlite2/README.md`](../../tests/SkyCD.Plugin.CdCollect.Tests/Fixtures/Sqlite2/README.md)
and other `Fixtures/<Format>/README.md` notes in the repository. The exact
export file names are whatever the wizard produced and must be recorded, not
renamed to the generic names above.

This project and directory **do not exist yet**, and this issue does not create
them. They are created by the implementation change that consumes the first
verified fixtures, together with its tests.

## License limit

Only export files produced by a user's own Data Crow installation from
donor-owned or invented catalog data may be committed. The following are
forbidden and must never enter the repository, tests, CI caches, or this
documentation:

- Data Crow source code, installers, distribution archives, or bundled
  libraries and resources (GPLv3, blocked by the dependency license policy).
- Copies of Data Crow documentation or help content.
- Third-party sample exports or catalogs of unknown provenance.
- Any binary executable or Data Crow runtime artifact.

The exports are user data, not Data Crow code, but they still require the
donor's explicit redistribution permission recorded in the provenance note.

## Blocking statement

**Implementation remains blocked.** No Data Crow importer, parser, recognizer,
plugin project, or shared-conversion work may start until verified,
redistributable fixtures with complete provenance land in the repository. The
implementation change must cite specific capture IDs for each fact it relies
on.

A capture or module is closed only when all of the following hold:

1. Every matrix cell for that module has an accepted file, or a written
   statement in this document records that specific capture as unobtainable.
2. The provenance record is complete, including donor permission and the
   PII-stripping confirmation.
3. Checksums are recorded and verified again during review.
4. The file layout, wizard settings, and copied-images state are recorded.
5. The four format facts above have been extracted from the accepted files and
   written down with their supporting capture IDs.

Partial donations close cells individually. A module without fixtures stays
blocked and this document continues to record its status.
